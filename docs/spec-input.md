## 1. Purpose

A live sales demonstration of multi-agent orchestration: several AI agents with fixed roles, under an Orchestrator, take a business request from intake to a reviewed deliverable that a human approves. The demo must (a) make the agents, their communication, and the orchestration visible, (b) prove the builder's capability, (c) help a non-technical prospect understand how the pattern works, and (d) double as a proof of concept for two real client workflows.

Audiences: the prospect in the room, the owner presenting, and sales staff learning the pitch.

Two workflows on one engine, differing only in configuration: electrical bid response (built first) and appraisal intake-to-report (second). The incoming documents are the bid request (the client's letter or email) and the tender package (the drawing set and specification).

## 2. Structure

Web application hosted under the Sterling AI domain (subdomain TBD). Two content tabs plus utility pages.

### 2.1 Introduction tab (public)
Static content served from `content/intro/*.md`, rendered in order: what it is; architecture; the agentic loop; the team; how agents differ; how this becomes real inside your AWS account; FAQ. Three diagrams rendered from the specs embedded in those files: architecture; the loop, which reuses the Demo loop strip component in a static, fully-lit state with the backward arrows labelled so the two stay consistent; and demo vs production. An embedded public Replay of one recorded clean run at the bottom. Content must be exportable to PDF through the Typst pipeline for the leave-behind.

### 2.2 Demo tab (behind shared login)
Single page, one workflow at a time, chosen with a workflow selector. Layout:
- Header: product name, workflow selector, page navigation in the order Pre-flight, Introduction, Demo, Settings (Pre-flight first because the presenter opens it before every meeting; the export orders them Demo, Introduction, Pre-flight, Settings, recorded in `docs/design-deviations.md`) with the pre-flight indicator (section 2.4), and the build stamp (git hash and date) in the Settings style. Every other page carries the same header without the workflow selector.
- Loop strip across the top: six stage nodes, forward arrows, backward arrows (Review to Work, Review to Assemble, Work to Intake), a retry counter badge on Review reading "retry N of M" where M is the maximum number of reworks, a human icon on Intake, Work, and Handoff. Node state is driven only by `stage.changed` events, in Team mode and Single-model mode alike: the current stage is lit, completed stages stay marked complete, the connector between two completed nodes fills, upcoming stages are idle, and a stage a forward transition skips renders bypassed (dimmed, dashed border), never idle. A stage label under the strip shows the `target_reason` of the latest `stage.changed`, replaced by the termination headline when the run ends. On every `stage.changed` the arrow between `from` and `to` pulses once, about 600 ms, forward arrows and backward arrows alike; Replay fires the same pulses because they are keyed to event ids.
- Composer: dataset dropdown (section 7), workflow selector, run mode switch (Team / Single model), model dropdown visible only in Single mode, Dry intake toggle beside the run mode switch (not in the design export; added in its switch style, see `docs/design-deviations.md`), Run, Pause, Stop, Replay controls with speed (1x / 4x). Pause is a presenter control that freezes dispatch between events: no new dispatch, in-flight calls complete, Resume continues; it emits `run.paused` and `run.resumed`. Stop ends the run with exit `stopped`. Controls whose behaviour is not yet built are disabled, not hidden.
- Event feed, left two-thirds: Slack-idiom message cards. One thread per sub-task: dispatched, then progress messages and tool calls as replies (`task.progress`, `tool.called`), then completed or blocker. Every thread renders collapsed to its one-line summary and stays collapsed until the presenter clicks its toggle; nothing auto-expands. While a task has a `task.dispatched` with no `task.completed` or `blocker.raised` yet, the collapsed header shows a live state on the agent avatar and the header border, in the same visual language as the active node in the loop strip: on at `task.dispatched`, off at `task.completed` or `blocker.raised`, driven by events only. The header shows the count of replies added since the thread was last collapsed. The blocker card, the question card, and the termination card stay open, because they are the human's door. Every agent message shows the agent card (section 4.2) and a small prompt toggle beneath it (section 2.5). Orchestrator events show their `reason` on click. Clarification, assumption, and blocker cards are visually distinct. While the run is paused on a blocker, the blocker card offers Answer and Escalate (section 3, stage 3). Verdict cards show severity-coded findings.
- Artifact panel, right third: page images of the compiled deliverable, refreshed in place on every `artifact.compiled` event, no flicker, scroll position preserved. Provenance tags are hover targets (section 2.6). A collapsible Compare strip above it holds the most recent Single-model output. At Handoff: Approve, Edit, Reject, Download PDF, Download run timeline. Edit and Reject are not in the design export and are added in its button style (see `design/README.md`).
- Meters strip: elapsed working time, ticking each second while the run works, held while the run waits on the human, stopped at termination; per-agent tokens and estimated cost accumulated from `meter.update` deltas, run total, Team vs Single comparison line, per-run cost ceiling indicator. Clicking an agent meter opens a detail row: calls, tokens in and out, cost, wall time, last event. Every `meter.update` carries `latency_ms`, the provider's reported latency, beside `wall_ms`, the measured wall time of the call. At termination the run writes `performance.json` (section 6), shown on the termination card behind a Performance toggle.
- Raw turns drawer at the bottom: the JSON event stream for the run, collapsed by default.
- Waiting-on-you banner when the run is paused for human input, with the batched questions and an answer form. Proposed defaults are pre-filled and editable.
- Termination card: rendered from `handoff.ready` when Handoff is entered, stating the exit determination and the Orchestrator reason, with Approve available while it is on screen; rendered from `run.terminated` for exits that do not pass through Handoff, and for `not_ready` and `blocker_escalated` it lists what is missing from the structured summary. `run.terminated` closes the card with the human decision where there was one. For `retry_exhausted` the card names the stop reason from `summary.stop_reason` (no progress, repeated finding, or maximum cycles). A Performance toggle on the card shows the per-agent, per-stage, and per-run summary from `performance.json`, with a download.

### 2.3 Settings page (behind shared login)
One row per agent seat showing the agent card. A model dropdown per seat listing every provider and model that has credentials configured in `.env`, plus local Ollama models detected at startup. Providers without credentials appear greyed. A change takes effect at the next stage dispatch (so a mid-run swap works), emits `model.changed`, and updates the grey model text everywhere immediately. Default roster in section 4.3. No credential entry.

### 2.4 Pre-flight page (behind shared login)
Checks and shows green or red per item: each model in the registry answers a minimal call (cloud models, probed at the same time, not applicable when the provider has no key) or is pulled (local models); Ollama reachable; Typst present and a test compile succeeds; page PNG export works; tunnel reachable from outside (if configured); disk space; `.env` completeness; the Introduction's public recording present; every dataset has a replay; the Reviewer and the Writer on different model families. Run before every demo. The rows are stored and the indicator in every page header is worked out from them against the seats in force and the run mode each time a page loads: red when a seat's model, the Ollama host a local seat needs, a seat provider's key, Typst, PNG export, or disk failed, or the login pair is missing in Cloud mode; amber when only the tunnel, the Introduction recording, a replay, or the model families failed; green otherwise, even when a model no seat uses failed; grey when nothing has been checked. A seat change in Settings rechecks the chosen model and the key for its provider.

### 2.5 Prompt toggle
Beneath every agent message in the feed, a small toggle expands to the exact prompt bundle used for that call, pretty-printed and sectioned: system instructions, context slice provided, task, tools available, model used. Always available, read-only, not a setting. Stored per call via `prompt_ref` in the event schema.

### 2.6 Provenance
The Writer tags every factual figure in the deliverable with the `event_id` of the specialist output it came from. In the artifact panel, hovering a tag scrolls the feed to the source message and highlights it. Nothing beyond hover.

### 2.7 Chat with agents
When the run is paused or finished, clicking an agent card opens a side conversation. The agent answers from its own system prompt and its current run context. Read-only with respect to the run: it cannot change instructions, state, or outputs. No persistence across runs. Chat is out of band: it is not an event, is not recorded, and is not replayed. It never touches the run, which is why it is allowed to leave no trace.

### 2.8 Access
Shared username and password from `.env`, protecting the Demo, Settings, and Pre-flight pages. Introduction tab is public.

### 2.9 Hosting and run modes
One codebase, two run modes chosen by config:
- Laptop mode (demo day): the full app runs on the presenter laptop, exposed through a Cloudflare Tunnel to the Sterling AI subdomain. Local models via Ollama at localhost.
- Cloud mode (always-on): the app runs on a small cloud host with cloud providers only; local model options are greyed out.

### 2.10 Frontend source
The Claude Design export in `design/` is the source of truth for appearance and stays untouched as reference. The application does not ship the Claude Design runtime or React. The export is flattened into static HTML, one CSS file with classes derived from the export's inline styles, and vanilla JS render functions driven by the event stream. The design-time state switcher, sample copy, and inline demo data are dropped or moved to fixtures. Acceptance: a side-by-side screenshot comparison against `design/screenshots/` for each screen and each Demo state shows no visible difference at 1920 by 1080. Known deviations between the export, the brief, and this spec are listed in `design/README.md`.

## 3. The agentic loop

Global rules: only the Orchestrator changes stage, talks to the human, writes the knowledge file, or ends a run. Every agent action is a typed event. Review continues while it makes progress and stops at a hard ceiling of `review_max_cycles` cycles per run (default 4, configurable); the rule is in stage 5. A Work to Intake route is not a review cycle; it has its own cap of one per run, and a second attempt becomes a blocker. Every backward arrow carries a reason and a target. `run.terminated` is always the last event of a run. Pause freezes dispatch between events: no new dispatch, in-flight calls complete, Resume continues; both are Orchestrator events with a reason.

### Stage 1, Intake
Owner: Intake Analyst. Input: raw request and attachments, client knowledge file, readiness checklist. Before reading anything, the Analyst runs `prepare_documents`, a deterministic tool (no model call) that splits every PDF in the dataset inputs into single-sheet PDFs, page PNGs, and one text file per sheet from the text layer under `runs/<run_id>/prepared/`, and writes `manifest.md` listing every sheet with its sheet number, title, discipline (A, E, M, S, P, other), "Issued for" stamp, revision date, page count, and legibility confidence. The Analyst reads `manifest.md` and the sheet text files, not the raw binder; specialists receive sheet files by reference in their task scope. One `tool.called` event per source file and one for the manifest show the preparation in the feed. The Orchestrator does not run this tool; it dispatches Intake as before. The readiness checklist reads the stamp on every sheet from the manifest and grades a set that is not Issued for Tender or Issued for Construction as an assumption. Outputs: structured brief; readiness verdict (Ready / Ready with assumptions / Not ready) with the checklist graded item by item; per-page legibility confidence; zero or more `clarification.needed` events, each with a proposed default and a blocking flag. Orchestrator behaviour: non-blocking gaps proceed on the default and emit `assumption.accepted`; blocking gaps are batched into one question set and the run pauses. Not ready terminates the run before Plan (exit `not_ready`). Dry intake mode stops after this stage regardless of verdict, with exit `dry_intake` and the readiness verdict on the summary. Backward arrows in: from Work when a specialist finds the brief incomplete, once per run. Answers to Intake clarifications are facts about the client: the Orchestrator appends each one to the knowledge file as soon as it is answered (`knowledge.appended` follows `clarification.answered`), whatever exit the run later takes. Blocker answers are about the file, not the client, and stay run-local.

### Stage 2, Plan
Owner: Orchestrator. Output: work plan with sub-tasks: the specialist sub-tasks plus Assemble as the final sub-task assigned to the Writer, each with assigned agent, dependencies, and visibility scope. Review is a stage, not a task, and is not in the plan. No human touchpoint. UI holds on the plan for a beat.

### Stage 3, Work
Owner: specialists, dispatched by Orchestrator. Each receives its sub-task, the brief, and only the tools and context in its scope. Independent sub-tasks run concurrently (a gather over independent tasks); dependent ones wait (Pricing waits for Estimator). During work a specialist emits `task.progress` messages and one `tool.called` event per tool invocation; both render as thread replies, and tool calls feed provenance. Outputs: structured results with provenance (tool, source, confidence), or a `blocker.raised` event. A blocker with `needs_human` pauses first: the Orchestrator emits `clarification.asked` carrying the blocker, the run pauses, and the blocker card offers two actions. Answer resumes at Work with the answer injected into the specialist's context. Escalate terminates with exit `blocker_escalated`. A specialist may route back to Intake with a reason, once per run.

### Stage 4, Assemble
Owner: Writer. Input: brief, all specialist outputs, deliverable template, client knowledge file. Output: markdown draft committed in versions; each commit emits `draft.committed`, triggers a compile, and emits `artifact.compiled` with page image paths. Every figure carries a provenance tag. Backward arrows in: from Review for writing or assembly findings.

### Stage 5, Review
Owner: Reviewer. Sees the brief, the compiled page images, and the reviewer criteria file. Does not see specialist reasoning, tools, or the Writer sources. Different model family from the Writer. Output: `review.verdict` with pass or fail, findings each with severity (blocker, major, minor), evidence, and recommended routing (Work plus named specialist, or Assemble). Minor findings do not fail a draft; they ride to Handoff as notes. Orchestrator decides: pass goes to Handoff. After a failing verdict at cycle c, rework continues only if all of the following hold: c is 1, or the count of blocker plus major findings is strictly lower than in the previous cycle; no finding in this cycle matches a finding from the previous cycle, compared on normalized evidence text and route target (stage and agent); c is below `review_max_cycles` from config (default 4); the cost ceiling has not tripped (a trip ends the run with its own exit). Rework dispatches to the routed stage and increments the retry counter. Otherwise the run terminates with exit `retry_exhausted`, the specific stop reason (`no_progress`, `repeated_finding`, `max_cycles`) recorded in `run.terminated.summary.stop_reason` and named on the termination card, and the findings go to Handoff unresolved.

### Stage 6, Handoff
Owner: Orchestrator. Entered on `reviewer_pass` and `retry_exhausted`. On entry the Orchestrator emits `handoff.ready` with the exit determination and the package for the human: final deliverable (PDF and page images), Reviewer verdict and unresolved findings, assumptions accepted, clarifications asked and answered, full event log. The human approves, edits, or rejects, recorded in `human.approved`. Approve: no further change. Edit: the human edits the deliverable markdown in place, one recompile (`draft.committed` and `artifact.compiled` with actor human), then terminate; there is no re-run through the loop. Reject: recorded with notes, then terminate with the same exit; a reject that re-enters the loop is product. Nothing is sent externally. Then `run.terminated` with the same exit value as `handoff.ready`.

### Exits
Eight exit values on `run.terminated`. Four narrative exits, the ones the Introduction copy describes: `reviewer_pass`, `retry_exhausted`, `blocker_escalated`, `not_ready` (fires from Intake). Four control exits, reserved for safety and control and not part of the demo narrative: `cost_ceiling`, `stopped` (the Stop button), `single_complete` (a Single-model run, section 5), `dry_intake` (Dry intake mode, after Intake whatever the verdict). Only `reviewer_pass` and `retry_exhausted` pass through Handoff; the others terminate directly and the termination card renders from `run.terminated`. The `summary` on `run.terminated` is structured, not free text, so the `not_ready` and `blocker_escalated` cards carry the list of what is missing without a Handoff package (section 6). For `retry_exhausted` it carries the `stop_reason`.

### Cost ceiling
A per-run estimated cost ceiling from config. The Orchestrator checks it after every `meter.update` and, on breach, terminates with `run.terminated` exit `cost_ceiling` before dispatching anything further, and escalates.

Model is a runtime attribute shown in small grey text (the `label` of the model object in section 6) and must always reflect the live configuration. Two names and two illustrated avatars per role (one male-presenting, one female-presenting), chosen at random per run; the name follows the avatar.

### 4.4 How agents differ
Instructions: Orchestrator manages; Analyst understands; specialists produce facts; Writer assembles; Reviewer finds fault. Writer and Reviewer have opposing success criteria on purpose.
Tools: each specialist has exactly the tools its trade needs. Writer has a template. Orchestrator and Reviewer have none.
Visibility: as in the roster table. Restricting context is what makes roles real; it also lowers cost and hallucination.

## 5. Single-model mode
Composer switch. Runs the same request through one model with a strong single prompt and no team. A Single-model run is its own `run_id` with `mode: single` and its own event stream: `run.started`, one `task.dispatched`, `task.completed` carrying the output, `meter.update`, `run.terminated` with exit `single_complete`. The loop strip tracks a Single-model run too: the run emits `stage.changed` into Intake, Work, Assemble, and Handoff with `stage` set, so Plan and Review render as bypassed; `run.started` and `run.terminated` keep `stage` null. The Compare strip reads from that run and shows the output with its own cost and time. Model chosen from the same provider registry as Settings. Purpose: contrast. Nothing else.

## 6. Event schema (draft; freeze before writing agents)

Envelope, every event:
```
event_id      uuid
run_id        uuid
seq           integer, monotonically increasing per run
ts            ISO 8601
type          string, from the list below
stage         intake | plan | work | assemble | review | handoff | null
              (null for run.started and run.terminated; in a Single-model run also null on every event other than stage.changed)
actor         agent | "human" | "system"
              agent is { agent_id, name, role, model }; model is { provider, model_id, label }; label is the grey text on the agent card
reason        string, required on every Orchestrator event, one sentence
prompt_ref    id of the stored prompt bundle for this call, present on agent messages
payload       object, type-specific
```

Event types and required payload fields:
- `run.started` { workflow, dataset_id, mode: team | single, roster: [agent cards] }  (actor Orchestrator, with reason)
- `stage.changed` { from, to, direction: forward | backward, target_reason }
- `intake.brief` { brief }
- `intake.readiness` { verdict: ready | ready_with_assumptions | not_ready, checklist: [{ item, status, note }], legibility: [{ page, confidence }] }
- `clarification.needed` { question_id, question, why_it_matters, proposed_default, blocking: bool }
- `clarification.asked` { question_ids: [], blocker: { blocker_id, task_id, agent_id, description } | null }  (Orchestrator, run pauses; carries the blocker when raised by one)
- `clarification.answered` { question_id, answer, action: answer | escalate }  (actor human; escalate is valid only for a blocker and leads to exit `blocker_escalated`)
- `assumption.accepted` { question_id, default_used }
- `plan.created` { subtasks: [{ task_id, agent_id, depends_on: [], scope: [] }] }  (includes the Assemble sub-task assigned to the Writer)
- `task.dispatched` { task_id, agent_id, inputs_summary }
- `task.progress` { task_id, agent_id, message }
- `tool.called` { task_id, agent_id, tool, args_summary, result_summary, duration_ms }
- `task.completed` { task_id, agent_id, result, provenance: [{ tool, source, confidence }] }
- `blocker.raised` { blocker_id, task_id, agent_id, description, needs_human: bool, route_back_to: intake | null }
- `draft.committed` { version, markdown_path, provenance_tags: [{ tag_id, source_event_id }] }  (actor Writer, or human for a Handoff edit)
- `artifact.compiled` { version, pdf_path, page_images: [] }
- `review.verdict` { verdict: pass | fail, findings: [{ id, severity: blocker | major | minor, evidence, route_to: work | assemble, agent_id | null }] }
- `retry.incremented` { count, budget }  (count is reworks so far; budget is the maximum reworks, review_max_cycles minus one)
- `handoff.ready` { exit_determination: reviewer_pass | retry_exhausted, package: { pdf_path, page_images: [], verdict_event_id, unresolved_findings: [], assumptions: [], clarifications: [], event_log_path } }  (Orchestrator, on entering Handoff)
- `human.approved` { decision: approve | edit | reject, notes }
- `knowledge.appended` { client_id, entries: [{ question_id, answer, source_event_id }] }  (Orchestrator, immediately after each Intake clarification is answered; blocker answers are not appended)
- `run.paused` { by: human }  (Orchestrator, with reason; no new dispatch, in-flight calls complete)
- `run.resumed` { by: human }  (Orchestrator, with reason)
- `model.changed` { agent_id, from_model, to_model }  (both are model objects { provider, model_id, label })
- `meter.update` { agent_id, call_id, tokens_in, tokens_out, wall_ms, latency_ms, est_cost }  (per-call delta; wall_ms is measured wall time, latency_ms the provider's reported latency; the UI and the run summary accumulate per agent and per run)
- `run.terminated` { exit: reviewer_pass | retry_exhausted | blocker_escalated | not_ready | cost_ceiling | stopped | single_complete | dry_intake, summary: { headline, missing: [{ item, note, source_event_id }], unresolved_findings: [finding ids], retries: { count, budget }, stop_reason: no_progress | repeated_finding | max_cycles | null, readiness_verdict: ready | ready_with_assumptions | not_ready | null, event_count, elapsed_ms, est_cost, human_decision: approve | edit | reject | null } }  (always the last event of a run; `missing` is filled for not_ready and blocker_escalated, `unresolved_findings` and `stop_reason` for retry_exhausted, `readiness_verdict` for not_ready and dry_intake; the card renders from these fields, not from free text)

Prompt bundle (stored, referenced by `prompt_ref`): { system, context_slice, task, tools: [], model }.

Recording: every run persists everything it needs to be replayed and audited under `runs/<run_id>/`: the ordered event log `events.jsonl`; `run.json`, the run manifest (run id, dataset id and a sha256 of its inputs, workflow, mode, agent mode, the roster at start with the full model object per seat, a config snapshot with `review_max_cycles`, the cost ceiling, the seat model entries and a sha256 of the config folder, the schema version, the app build stamp, start and end times, the exit, and an index of every file in the folder); every prompt bundle under `prompts/<prompt_ref>.json` (system, context slice, task, tools, model object); every raw model response under `responses/<prompt_ref>.json` (each attempt's text, accepted or rejected with the reason, and every tool call's full arguments and result); every file created during the run (`prepared/` documents, `drafts/` markdown versions, the compiled PDF and page PNGs from S4, `knowledge.md` and the `knowledge.diff` appended by the run); `metrics.json` and `seat-calls.jsonl` (rule 10 in `CLAUDE.md`); and `performance.json`, written at termination: per agent and per call the tokens in and out, wall time, estimated cost, and provider latency; per stage the wall time and number of dispatches; per run the total time, total cost, number of review cycles, termination exit and stop reason, count of clarifications asked and assumptions made, and tool calls by tool. Replay is reproducible from this folder alone, with no access to the dataset or the providers. Replay reads that folder and re-emits the recorded events verbatim over the same SSE endpoint, with the original `run_id` and `event_id` values and the original relative timing scaled by speed. Replay plays the most recent recording for the selected dataset and falls back to the dataset's `golden-events.jsonl` when no recording exists; there is no run browser. The public Replay on the Introduction tab is an unauthenticated read-only endpoint pinned to one `run_id` from config; it serves only that recording and nothing else.

## 7. Scenario datasets
Dropdown in the composer. Each dataset is a folder under `datasets/` with `README.md` (scenario, planted defects, expected stage sequence and exit), `inputs/` (request and attachments), `fixtures/` (price list, CRM, comparables as applicable), `knowledge.seed.md`, `brand.yaml` (prospect name and logo for the deliverable cover), and `golden-events.jsonl`.

Initial electrical bid response scenarios:
1. Clean run: passes Review first time. Exit `reviewer_pass`.
2. Planted inconsistency: panel schedule states 200A where the single-line shows 225A. Estimator flags or Reviewer catches; one rework; pass. Exit `reviewer_pass` with retry count 1.
3. Missing sheet: panel schedule sheet absent. Estimator raises a blocker; the run pauses; the presenter chooses Escalate because a missing sheet cannot be supplied live. Exit `blocker_escalated`. The golden log records the Escalate path.
4. Missing price: one BOM item absent from the fixture. Pricing exception surfaces at Handoff as a minor finding. Exit `reviewer_pass`.
5. Not ready: no deadline and no specifications. Intake stops the run. Exit `not_ready`.
6. Prospect own: empty slot for a real prospect file. Expected behaviour determined by Dry intake before the meeting.
7. Prospect A (`prospect-a`): a real bid package, an Issued for Construction architectural set with an electrical set issued for permit, carrying a real disagreement between a panel note on one sheet and the bus rating on the panel schedule. Expected: one Review fail routed to the Estimator, rework, pass. Exit `reviewer_pass` with retry count 1; the issue stamp surfaces as an assumption.
8. Prospect B (`prospect-b`): a real bid package that is internally consistent, under the rules of its occupancy type. Exit `reviewer_pass`.
9. Prospect C (`prospect-c`): a real package with architectural drawings only and no electrical set. Exit `not_ready`.

Scenarios 7 to 9 are scaffolds until the owner supplies the inputs, redacted (names, emails, phones on every sheet) and with the prospect's consent; the inputs are never committed and no drawing is fabricated. Their golden logs are recorded from the first verified live run of each. This repository is public, so a prospect, their project, their site, and any defect in a set they shared are not named in tracked files; the owner keeps the mapping locally under `datasets/`, which is ignored.

## 10. Acceptance criteria for demo v1
- All six scenarios run live and terminate with the expected exit; the test suite passes against golden logs.
- The loop strip, feed, artifact panel, and meters render only from events; disconnecting the agents and running Replay produces an identical display.
- Every screen and every Demo state matches `design/screenshots/` in a side-by-side comparison at 1920 by 1080 with no visible difference.
- Every run's last event is `run.terminated`; Stop ends a run with exit `stopped`.
- A clarification or blocker answer resumes the run; Escalate on a blocker terminates with `blocker_escalated`.
- Swapping any seat in Settings changes the grey model text everywhere within one second and the next dispatch uses the new model.
- Every agent message has a working prompt toggle showing the actual bundle used.
- Hovering any provenance tag highlights the correct source message.
- Pre-flight goes green on the presenter laptop in Laptop mode.
- Leave-behind command produces three PDFs without manual steps.
- No em dash appears in any file, prompt, or rendered copy (enforced by a lint step).
- Every agent thread starts collapsed; the activity indicator turns on at `task.dispatched` and off at `task.completed` or `blocker.raised`, and nothing else.
- The loop strip shows the same node states, stage label, and arrow pulses in a live run and in its Replay.
- A run folder replays with the datasets folder removed and no provider credentials.
- Every `retry_exhausted` termination card names its stop reason.
